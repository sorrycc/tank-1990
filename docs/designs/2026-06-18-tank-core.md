# Tank 1990 — F1 Tank Core (controllable tank + pooled bullets on a test arena)

> Design doc for **F1 Tank Core**, the first GAMEPLAY feature of Tank 1990 (a faithful Battle
> City / 坦克大战 clone). Format mirrors the read-only reference `dead-cell` design docs EXACTLY:
> Background → Requirements Summary → Acceptance Criteria → Decision Log → Design → Files →
> Verification. F0 stood up the booting skeleton (six scenes, pure RNG, defensive save, shared
> constants, a green `typecheck`/`build`/`verify`). F1 makes a tank you can DRIVE: a single
> `Input` owner producing a per-frame two-player intent snapshot, a plain `Tank` entity with
> classic grid-aligned 4-direction movement + facing + a fire cooldown + a per-tank live-bullet
> cap, a pooled `Bullet` (zero per-frame allocation), and a `GameScene` that builds a centered
> steel-walled test arena, samples input ONCE/frame, and ticks tanks + bullets on a dt measured
> in SECONDS. No terrain generator, no enemies, no eagle, no power-ups yet (YAGNI — each lands in
> its own later feature). This is the controllable-tank FOUNDATION every combat feature extends.

## 1. Background

Battle City is a **top-down grid** tank shooter: tanks span ~2×2 tiles, move in four cardinal
directions snapped to the grid, and fire straight bullets along their facing. F0 delivered the
skeleton — a booting Phaser+Vite+TS app, the six-scene flow (Boot → Title → Hub → Game + a
parallel HUD → GameOver), the PURE `config/constants.ts` (grid 13×13, `TILE_SIZE`, `TANK_SPEED`,
`BULLET_SPEED`, `FIRE_COOLDOWN`, `MAX_PLAYER_BULLETS`, the centered-playfield layout math), the
byte-identical `mulberry32` RNG, the defensive save, and the headless verifier — all green. The
`GameScene` is currently a STUB that draws one placeholder playfield rectangle.

F1 turns that stub into a **drivable tank sandbox**. It introduces the three Phaser-coupled
gameplay primitives the whole combat system stands on, mirroring the reference's layered
modules + conventions EXACTLY:

- **`src/core/Input.ts`** — the SINGLE owner of keyboard bindings (DRY), producing a per-frame
  intent snapshot. The reference owns ONE player's bindings; Tank 1990 is **2-player local
  co-op** (locked decision), so this snapshot carries **P1** (WASD move + a fire EDGE) and **P2**
  (arrow move + a distinct, non-conflicting fire EDGE). Each player exposes a 4-direction intent
  + a fire edge (`JustDown`, SOLE-owned here — like the reference's jump/dodge/attack edges).
- **`src/entities/Tank.ts`** — a plain class (the reference's `Player` shape: HOLDS a Phaser
  rectangle + an Arcade body, owns its feel constants + state, is news'd-up and ticked by the
  scene, NOT on the display-list lifecycle). Classic Battle City movement: a tank moves
  CONTINUOUSLY in its faced direction and SNAPS to the grid on the cross axis. Facing, a fire
  cooldown, a per-tank live-bullet cap, a `side` tag (`'player'|'enemy'`) + a `behavior` tag for
  later (the enemy FSM is a LATER feature — F-enemies).
- **`src/combat/Bullet.ts` (a `BulletPool`)** — a pooled bullet adapted DIRECTLY from the
  reference's `combat/ProjectilePool.ts` discipline: a FIXED set of pre-created rectangle+body
  members, acquire/release, ZERO per-frame allocation. Owner side, velocity along facing at
  `BULLET_SPEED`, despawns off the playfield. (Bullet↔terrain/tank/eagle collision is a LATER
  combat feature; F1 only despawns at the arena bounds.)
- **`src/scenes/GameScene.ts`** — the top-down run scene. An Arcade world with **gravity 0**
  (F0's Decision 3), a centered SQUARE test arena bounded by STEEL border walls (static bodies),
  the camera fixed on the playfield. Spawn P1 (and P2 if 2-player), sample `Input` ONCE/frame,
  tick tanks + the bullet pool, fire spawns pooled bullets. dt is handled in **SECONDS** at the
  boundary (`delta/1000`, clamped to `MAX_DT`).

**Conventions mirrored from `dead-cell` (read-only, NEVER modified):** the PURE/COUPLED split
(`config/*` stays Phaser-free; `core/Input`, `entities/Tank`, `combat/BulletPool`, scenes are
Phaser-coupled and NEVER imported by the verifier); the SINGLE `Input` owner producing one
per-frame snapshot, with each fire edge read via `JustDown` exactly once (sole owner); a plain
entity that holds a `collider` (owns the body) + a visible `rect`, ticked by `update(dt, …)` with
`dt` in SECONDS; the object-pool discipline (fixed members, acquire/release, no per-frame alloc,
hand-integrated position so a future hit-stop can freeze them); `dt = Math.min(delta/1000,
MAX_DT)`; heavy intent-revealing comments citing the section + AC + Decision numbers.

## 2. Requirements Summary

**Goal:** A controllable tank core on a hand-made test grid (no terrain generator, no gravity
world): both players drive a grid-aligned 4-direction tank with facing, and fire pooled bullets
that travel straight and despawn at the arena bounds — all green on `typecheck`/`build`.

**In scope (F1):**

- **`src/core/Input.ts`** — the SINGLE bindings owner. `sample()` returns ONE per-frame snapshot
  with, PER PLAYER (`p1`, `p2`): a 4-direction intent (`up/down/left/right` booleans + a derived
  `dirX`/`dirY`) and a `firePressed` EDGE (sole-owned `JustDown`). P1 = **WASD** move + **J**
  fire; P2 = **arrow keys** move + **Numpad0** fire (a distinct, non-conflicting fire key — see
  Decision 4). No jump/dodge/skill keys (YAGNI — Battle City has none).
- **`src/entities/Tank.ts`** — a plain class: a `collider` rectangle owning a square Arcade body
  (`TANK_SIZE`≈2 tiles) + a visible `rect` + a small `barrel` facing marker. Classic grid-aligned
  4-dir movement (continuous along the faced axis, snap-to-grid on the cross axis — Decision 5),
  `facing` (`'up'|'down'|'left'|'right'`), a fire `cooldownTimer`, a per-tank live-bullet count +
  cap (`maxBullets`), a `side` (`'player'|'enemy'`) + a `behavior` tag (`'player'` for F1).
  `update(dt, intent)` with `dt` in SECONDS. A `tryFire(pool)` gated by cooldown + the live cap.
- **`src/combat/BulletPool.ts`** — a pooled `Bullet` (rectangle + Arcade body), adapted from the
  reference `ProjectilePool`: fixed members, `acquire(owner)` / `release` / `releaseAll`, hand-
  integrated travel at `BULLET_SPEED` along the owner's facing, despawn off the playfield bounds.
  Each live bullet carries its `ownerSide` + a back-reference to the firing tank (so the tank's
  live-bullet count decrements on release — the classic "you can only have N shots out" rule).
- **`src/scenes/GameScene.ts`** — replace the placeholder: gravity 0; a centered SQUARE test
  arena (the F0 playfield rect) bounded by FOUR STEEL border walls (static Arcade bodies); the
  camera fixed on 1280×720 (no follow — the playfield is fully on-screen). Spawn P1 at a grid cell
  + (if 2-player) P2 at another; `new Input(this)`; one `BulletPool`. Per frame: `dt =
  min(delta/1000, MAX_DT)`; `sample()` ONCE; on each player's `firePressed`, `tank.tryFire(pool)`;
  tick both tanks + the pool; collide tanks↔walls + tanks↔tanks (no overlap).
- **A 2-player flag** — `TWO_PLAYER` in `constants.ts` (default `true`). When off, only P1 spawns
  and only P1's intent is read (single-player works; P2 simply absent).
- **Constants (added to the PURE `constants.ts`):** `TANK_SIZE` (the ~2-tile square body),
  `STEEL_WALL_THICKNESS`, `TWO_PLAYER`, `MAX_DT` (the dt clamp — shared so the verifier/HUD/later
  features read ONE owner), `LANE_SNAP_EPSILON` (the turn-time re-center dead-band — D5/D6). Existing
  `TANK_SPEED`/`BULLET_SPEED`/`FIRE_COOLDOWN`/`MAX_PLAYER_BULLETS`/`PLAYFIELD_*`/`TILE_SIZE`/
  `SUB_CELL_SIZE` are REUSED (no new copies, DRY).

**Out of scope (F1 — later features):** terrain tiles (brick/steel/water/trees/ice) + the seeded
13×13 stage GENERATOR (F2) + its verifier sweep; bullet↔terrain / bullet↔tank / bullet↔eagle
COLLISION + damage; the eagle base; enemy tanks + the ONE FSM (a `behavior` tag is reserved now
but unused); the 4 enemy types; power-ups; the boss; score/lives/HUD readouts; i18n strings; the
Hub upgrade trees + `applyUpgrades`. F1 ships ONLY a drivable tank that fires despawning bullets
in a walled box.

## 3. Acceptance Criteria

> All testable. §7 maps each AC to a `typecheck`/`build` check, a code-presence grep, or a manual
> `npm run dev` drive-test (F1 adds NO verifier assertions — `BulletPool`/`Tank`/`Input`/scene are
> Phaser-coupled, so the headless verifier must NOT import them; it stays the F0 stub).

1. **AC1 — Single Input owner, two-player snapshot.** `src/core/Input.ts` is the ONLY file that
   maps keycodes (no scene/entity hard-codes a key). `sample()` returns one snapshot
   `{ p1, p2 }`; each `PlayerIntent` exposes `up/down/left/right` (held booleans), `dirX`/`dirY`
   (∈ {−1,0,1}), and `firePressed` (an EDGE).
2. **AC2 — Distinct, sole-owned fire edges.** P1 fire = **J**, P2 fire = **Numpad0** — distinct,
   and neither collides with the other player's MOVE keys (WASD vs arrows). Each fire edge is read
   via `Phaser.Input.Keyboard.JustDown` EXACTLY ONCE per frame, inside `Input.sample()` (the sole
   owner), so a held fire key fires once per press, and `GameScene` calls `sample()` once/frame.
3. **AC3 — Both players move 4-dir grid-aligned + face the move direction, NEVER diagonally.**
   Holding a P1 (WASD) or P2 (arrow) direction drives that tank CONTINUOUSLY along that cardinal axis
   with exactly ONE `body.velocity` component non-zero and the cross component held at exactly 0
   (so Arcade can never integrate a diagonal — D5/§5.3 step 3); on a TURN to a new cardinal the tank
   discretely re-centers to its nearest `SUB_CELL_SIZE` lane (a one-shot snap, not a blended
   per-frame diagonal correction — §5.3 step 4); the tank's `facing` updates to the held direction
   and the barrel marker points that way. Opposing keys on one axis cancel to 0 (no jitter), and the
   re-center has an `LANE_SNAP_EPSILON` dead-band so it never oscillates around a lane center.
4. **AC4 — Fire spawns pooled bullets respecting cooldown + per-tank cap.** A fire edge spawns ONE
   bullet from the tank's muzzle along its facing IFF the fire cooldown has elapsed AND the tank's
   live-bullet count `< maxBullets` (`MAX_PLAYER_BULLETS`). Otherwise the press is a no-op. The
   bullet comes from the POOL (no per-shot allocation after warm-up); the live count increments on
   fire and decrements on release.
5. **AC5 — Bullets travel straight + despawn at the arena bounds.** A live bullet moves in a
   straight line at `BULLET_SPEED` along the facing it was fired with, and is RELEASED back to the
   pool when it leaves the playfield bounds (it never flies forever). On release the firing tank's
   live count decrements (so a new shot is allowed).
6. **AC6 — Tanks collide with the steel arena walls.** The centered square arena is bounded by
   four STEEL border walls (static Arcade bodies); a tank driving into a wall STOPS at it (no
   tunnel, no escape). Tanks also collide with each other (no overlap).
7. **AC7 — dt in SECONDS at the boundary, clamped.** `GameScene.update(_, delta)` computes
   `dt = Math.min(delta/1000, MAX_DT)` ONCE and passes that (SECONDS) to every `tank.update(dt,…)`
   and `pool.tick(dt)`. No feel/cooldown/travel formula consumes the raw millisecond `delta`. A
   tab-refocus spike can't teleport a tank/bullet through a wall (the clamp bounds one step).
8. **AC8 — Two-player flag.** `TWO_PLAYER` (in `constants.ts`, default `true`) gates P2: with it
   `true`, P2 spawns + its intent is read; with it `false`, only P1 spawns + is read (single-
   player works; P2 absent, no errors). `Input.sample()` ALWAYS returns both `p1`+`p2` (cheap,
   pure key reads); the SCENE decides whether to spawn/drive P2 (SOLID — Input has no game policy).
9. **AC9 — Pooling, zero per-frame allocation.** `BulletPool` pre-creates a FIXED set of
   rectangle+body members in its constructor; `acquire`/`release` reuse them (the `find(!active)`
   + reset pattern); `tick(dt)` hand-integrates position with NO allocation in the steady state
   (mirrors the reference `ProjectilePool`).
10. **AC10 — Pure/coupled split preserved.** `core/Input.ts`, `entities/Tank.ts`,
    `combat/BulletPool.ts`, and the scenes import Phaser and are NEVER imported by
    `scripts/verify-gen.mjs`. `config/constants.ts` stays PURE (no Phaser) — F1's new constants
    (`TANK_SIZE`, `STEEL_WALL_THICKNESS`, `TWO_PLAYER`, `MAX_DT`, `LANE_SNAP_EPSILON`) are added
    there, and the verifier
    continues to import it headlessly under node (its existing `DESIGN_WIDTH` assert still passes).
11. **AC11 — Green gate.** `npm run typecheck` (strict) and `npm run build` exit 0; `npm run
    verify` stays green (unchanged F0 stub — F1 adds no headless assertions, per AC10). No network
    `load.*`; programmer-art primitives only (rectangles), runs offline / from `file://`.

## 4. Decision Log

> Each decision notes how it stays KISS/YAGNI/DRY/SOLID and preserves the pure/coupled split.

1. **D1 — Mirror the reference's THREE coupled patterns 1:1.** `Input` = the single-owner snapshot
   producer; `Tank` = a plain `Player`-shaped entity (holds `collider` body + visible `rect`,
   ticked by the scene, off the display-list lifecycle); `BulletPool` = `ProjectilePool`'s exact
   pooling discipline. *Rationale:* the brief mandates mirroring `dead-cell` EXACTLY. Reusing three
   proven shapes is KISS/DRY and keeps every later combat feature (collision, damage, enemies,
   power-ups) plugging into the SAME seams the reference uses. No new architecture is invented.
2. **D2 — One snapshot carries BOTH players; the SCENE owns the 2-player policy (SOLID).**
   `Input.sample()` always returns `{ p1, p2 }` — two `PlayerIntent`s. It does NOT read `TWO_PLAYER`
   or decide who exists; it just reads keys (pure, cheap). `GameScene` reads `TWO_PLAYER` and
   decides whether to spawn/drive P2. *Rationale:* keeps Input a dumb, single-responsibility
   bindings owner (SOLID) — the reference's Input likewise has no game policy. Co-op friendly-fire,
   spawn counts, and the flag are GAME concerns the scene owns. Returning both is YAGNI-safe (two
   tiny structs/frame, no allocation pressure worth optimizing).
3. **D3 — A `PlayerIntent` is 4 held booleans + derived `dirX`/`dirY` + a `firePressed` edge.**
   The reference collapses horizontal to `moveX ∈ {−1,0,1}`; Tank 1990 needs BOTH axes. We expose
   the four held booleans (so the Tank's grid-snap logic can read raw direction priority) AND the
   derived `dirX = right−left`, `dirY = down−up` (∈ {−1,0,1}) for convenience. Opposing keys cancel
   to 0 (KISS — no last-key tracking, mirroring the reference's `moveX` both-pressed→0). *Rationale:*
   minimal, intent-revealing shape; the Tank reads it without re-touching Phaser keys (the single
   `JustDown`-owner invariant). The fire edge is `JustDown`-detected here and ONLY here (D1/AC2).
4. **D4 — P1 fire = J, P2 fire = Numpad0 (distinct, non-conflicting).** P1 moves on WASD; P2 moves
   on the arrows. Fire keys must avoid BOTH movesets AND each other. J sits in the left-hand cluster
   near WASD (the reference already uses J for attack — proven comfortable). **Numpad0** is the P2
   fire: it's on the right side near the arrow cluster, collides with NOTHING (WASD/arrows/J), and
   avoids the `'/'`+`RShift` pair the brief floated (RShift can be a sticky-keys trap and `/`
   overlaps some browser shortcuts). *Rationale:* a single, unambiguous binding per player kept in
   ONE owner (DRY); the choice is documented so a later rebind has a rationale to weigh. (If a
   keyboard lacks a numpad, a later feature can add a rebind UI — YAGNI now.)
5. **D5 — Classic Battle City movement: ONE velocity component non-zero, with a DISCRETE turn-time
   re-center (NOT a per-frame blended diagonal).** Steady driving is strictly single-axis: the body
   moves at `±TANK_SPEED` along the faced cardinal and the CROSS-axis velocity component is held at
   **exactly 0**. Setting BOTH components of `body.velocity` to non-zero in one frame would make
   Arcade integrate a true diagonal, directly violating AC3 ("never moves diagonally") — so the
   design FORBIDS that. Cross-axis re-alignment is therefore NOT a continuous correction velocity
   blended into steady motion; it is a **one-shot discrete SNAP fired only on a TURN** (when `facing`
   changes to a new cardinal whose driving axis differs from last frame's). On that single turn frame
   we re-center the cross coordinate to its lane, then from the next frame onward drive purely along
   the one faced axis with the cross component = 0. No held direction → both components 0 (idle).
   Both keys on one axis → that axis contributes 0. We pick exactly ONE driving axis per frame
   (prefer the still-held current facing axis, else the newly-pressed axis) so motion is strictly
   4-directional. *Rationale:* this IS the genre feel (you cannot drift between lanes; turning
   re-aligns you to the grid) AND it makes the no-diagonal invariant structural, not emergent — there
   is no frame where two velocity components are both non-zero, so Arcade can never integrate a
   diagonal. The snap is plain grid math over the existing `TILE_SIZE`/`SUB_CELL_SIZE` (DRY).
6. **D6 — Turn-time re-center = a VELOCITY-aligned snap that respects the collider, never a raw
   teleport, and never runs while a collision is being resolved.** The re-center keeps D6's
   velocity-only commitment: we do NOT hand-write `body.x`/`body.y` against Arcade. The snap targets
   the nearest **`SUB_CELL_SIZE` (24 px) lane**, computed on the body's TOP-LEFT corner relative to
   the playfield origin (see §5.3 for the exact formula — `TANK_SIZE = TILE_SIZE*2−4 = 92` is NOT a
   multiple of 24, so the target is a corner-snap, NOT a center-snap, to keep the formula clean and
   exact). The lane PITCH is unambiguously `SUB_CELL_SIZE`, not `TILE_SIZE`: classic Battle City
   quantizes tank motion to the half-tile (24 px) lattice, so a tank can sit on every 24 px lane, not
   only every 48 px one. We apply the re-center as a **single one-shot write to `body.position[cross]`
   on the turn frame** (NOT a velocity nudge — the cross VELOCITY stays exactly 0, so no diagonal is
   introduced), and only when the body is NOT currently touching/blocked on the cross axis
   (`!body.blocked[cross] && !body.touching[cross]`), so the snap never fights a wall/tank collider
   Arcade is resolving that frame — if blocked, the snap is skipped and retried on the next clear
   turn frame. A **dead-band** stops it from ever jittering: if the
   corner is already within `LANE_SNAP_EPSILON` of its target lane the snap is a no-op (no oscillation
   around lane center, no per-frame fight with Arcade). *Rationale:* hand-teleporting fights Arcade's
   position write-back (the reference's review BLOCKER #2 lesson). Gating the snap on
   `!blocked/!touching` + an epsilon dead-band keeps collision (AC6) authoritative and the body
   jitter-free, while preserving the "Arcade owns the body" contract. The visible `rect` + `barrel`
   are positioned TO the body each frame (the reference's collider/rect split).
7. **D7 — `Tank` carries `side` + `behavior` tags now; the FSM is YAGNI.** `side:'player'|'enemy'`
   gates friendly-fire/targeting later; `behavior:'player'` is a placeholder string the enemy FSM
   feature will extend (`'basic'|'fast'|'power'|'armor'|'boss'`). F1 only ever constructs
   `'player'` tanks. *Rationale:* adding the two tag FIELDS now (one struct slot each) means the
   enemy/boss features reuse the SAME `Tank` entity + the ONE FSM (a locked decision) without a
   refactor — but we build NO AI now (YAGNI). The fields are inert for player tanks.
8. **D8 — `BulletPool` adapted from `ProjectilePool`, trimmed to F1 needs (KISS/YAGNI).** Keep the
   fixed-members + acquire/release/`releaseAll` + hand-integrated `tick(dt)` discipline and the
   despawn-off-bounds release. DROP the reference's per-shot dedup `hitSet`, the 2-D aim, the
   pierce, the status, and the `onRelease` hook — F1 has no collision targets yet (bullets only
   despawn at bounds). Each bullet stores `ownerSide` + a back-ref to the firing `Tank` so release
   decrements that tank's live count. *Rationale:* copy the proven pooling SHAPE (so a later combat
   feature re-adds dedup/collision exactly as the reference does) but ship only what F1 uses (no
   speculative collision plumbing). Zero per-frame allocation (AC9) is preserved — the `find(!active)`
   acquire + cleared reuse, no `new` in `tick`.
9. **D9 — `MAX_DT` + the dt-in-seconds boundary, owned ONCE in `constants.ts`.** Add `MAX_DT = 1/30`
   to the PURE constants; `GameScene.update` computes `dt = Math.min(delta/1000, MAX_DT)` once and
   passes SECONDS everywhere (AC7). *Rationale:* the project's dt convention (and the reference's
   review BLOCKER #1) is dt-in-seconds at the boundary, clamped so a refocus spike can't tunnel a
   fast body through a wall. Owning `MAX_DT` in the single PURE constants owner (DRY) lets later
   features (enemy ticks, a future verifier of feel math) read the SAME clamp. `constants.ts` stays
   Phaser-free, so the verifier still imports it headlessly (AC10).
10. **D10 — Steel arena = four static-body border walls drawn as rectangles; camera fixed.** Build
    the test arena as the F0 centered playfield rect with FOUR thin STEEL rectangles (static Arcade
    bodies) hugging its inner edges; tanks collide with them (AC6). The camera is NOT a follow cam —
    the whole 624px playfield fits in 1280×720, so the camera stays fixed (KISS). *Rationale:* a
    hand-made test grid (the feature's stated scope) with REAL collision, using only primitives
    (AC11), reusing the F0 `PLAYFIELD_*` layout (DRY). The real terrain grid + a generated stage
    replace this hand-made arena in F2 — so the arena is deliberately minimal (YAGNI), just enough to
    prove movement, walls, firing, and despawn.
11. **D11 — No verifier additions (F1 stays the F0 stub).** F1 adds NO assertions to
    `scripts/verify-gen.mjs`. *Rationale:* the verifier may import ONLY pure modules. F1's logic
    lives in Phaser-coupled files (`Input`/`Tank`/`BulletPool`/scene) which the verifier must NOT
    import (AC10) — and the one pure thing F1 touches (the new constants) is data, not an algorithm
    with an invariant worth pinning. The real headless gate is the F2 seeded-stage sweep. Keeping the
    verifier untouched preserves the pure/coupled split and keeps `npm run verify` green (AC11).
12. **D12 — Fire is resolved in the SCENE off the edge, the Tank only fires when asked (SOLID).**
    `GameScene` reads `intent.firePressed` and calls `tank.tryFire(pool)`; `tryFire` checks the
    cooldown + the live cap and, if allowed, acquires a bullet from the pool. The Tank owns the
    cooldown/cap; the SCENE owns the pool (the world resource). *Rationale:* mirrors the reference's
    `player.attack()` (latch intent) → scene spawns the effect split — the entity owns its gating
    state, the scene owns the shared world pool (SOLID). The Tank never reaches into scene globals.

by their first feature — this one) and rewrites the `GameScene` stub:


### 5.2 Key types & constants

**`src/config/constants.ts`** (PURE — no Phaser; F1 ADDS these, reusing every existing value):

- `TANK_SIZE = TILE_SIZE * 2 - 4` — the square tank body (~2 tiles, a hair inset so two tanks in
  adjacent lanes don't perpetually graze). Derived from the existing `TILE_SIZE` (DRY).
- `STEEL_WALL_THICKNESS = 8` — the border-wall rectangle thickness (px).
- `TWO_PLAYER = true` — the co-op flag (D2/AC8). The SCENE reads it; Input ignores it.
- `MAX_DT = 1 / 30` — the per-step dt clamp in SECONDS (D9/AC7), the single owner.
- `LANE_SNAP_EPSILON = 0.5` — the dead-band (px) for the turn-time cross-axis re-center (D5/D6,
  §5.3 step 4): if the body's cross-corner is within this of its nearest `SUB_CELL_SIZE` lane the
  snap is a no-op, so the re-center can never oscillate or fight Arcade frame-to-frame. Sub-pixel,
  so the corner is visually lane-aligned; the single PURE owner so any later tuning is DRY.

(Existing reused, NO new copies: `TANK_SPEED`, `BULLET_SPEED`, `FIRE_COOLDOWN`,
`MAX_PLAYER_BULLETS`, `TILE_SIZE`, `SUB_CELL_SIZE`, `PLAYFIELD_X/Y/W/H`, `DESIGN_*`, `UI_FONT`.)

**`src/core/Input.ts`** (Phaser-coupled):

```ts
export interface PlayerIntent {
  up: boolean; down: boolean; left: boolean; right: boolean  // raw held cardinal keys
  dirX: number    // right − left  ∈ {−1,0,1}
  dirY: number    // down  − up    ∈ {−1,0,1}
  firePressed: boolean  // a JustDown EDGE (sole-owned here)
}
export interface InputSnapshot { p1: PlayerIntent; p2: PlayerIntent }
export class Input {
  constructor(scene: Phaser.Scene)   // addKeys: W/A/S/D + J (p1); UP/DOWN/LEFT/RIGHT + NUMPAD_ZERO (p2)
  sample(): InputSnapshot            // called EXACTLY once per frame by GameScene
}
```

`sample()` reads `isDown` for the eight move keys and `Phaser.Input.Keyboard.JustDown` for the two

### 5.3 Algorithms

**Input.sample() (once/frame).** Read the eight move `isDown`s + two fire `JustDown`s; build two
`PlayerIntent`s; return `{ p1, p2 }`. Pure read, no side effects, no allocation worth avoiding (two
small literals/frame).

**Tank.update(dt, intent) — order:**
1. **Cooldown decay:** `cooldownTimer = max(0, cooldownTimer − dt)`.
2. **Pick the move axis (4-dir, no diagonal — D5):** compute `dirX`/`dirY` from the intent (opposing
   keys on an axis cancel to 0). If NEITHER axis is held → the tank is idle this frame (skip to 3
   with no driving axis). Otherwise choose exactly ONE driving cardinal:
   - if the axis of the CURRENT `facing` is still held, keep driving that axis (no turn);
   - else adopt the newly-pressed axis (a TURN). Set `facing` to the chosen cardinal.
   Record `turned = (the chosen driving axis differs from the axis we drove last frame)`. This makes
   `turned` true ONLY on the frame a player switches between a horizontal and a vertical cardinal.
3. **Drive — exactly ONE velocity component non-zero (D5):** along the faced (driving) axis set the
   body velocity to `±TANK_SPEED`; set the **cross-axis velocity component to exactly 0**; if idle,
   set BOTH to 0. We never set both components non-zero in the same frame — Arcade therefore never
   integrates a diagonal (AC3 is structural). Concretely, for a horizontal facing
   `setVelocity(±TANK_SPEED, 0)`; for a vertical facing `setVelocity(0, ±TANK_SPEED)`; idle
   `setVelocity(0, 0)`.
4. **Turn-time re-center — a DISCRETE, collision-aware, velocity-only snap (D5/D6), run ONLY when
   `turned`:** on a non-turn frame do NOTHING here (steady single-axis driving already holds the
   cross velocity at 0, so the tank stays in its lane). On a turn frame, re-center the body's
   CROSS-axis corner to its nearest `SUB_CELL_SIZE` (24 px) lane, using this exact formula (cross =
   the axis perpendicular to the new driving axis; `origin = PLAYFIELD_X` for a vertical-corner snap
   when turning to up/down, `PLAYFIELD_Y` when turning to left/right):
   ```
   corner       = body.position[cross]                         // body top-left on the cross axis
   laneIndex    = Math.round((corner − origin) / SUB_CELL_SIZE)
   target       = origin + laneIndex * SUB_CELL_SIZE           // nearest 24 px lane, corner-aligned
   delta        = target − corner
   ```
   Apply the snap with these GUARDS, in order:
   - **Dead-band:** if `Math.abs(delta) <= LANE_SNAP_EPSILON` → no-op (already lane-aligned; this is
     what stops per-frame oscillation around lane center).
   - **Collision guard:** if `body.blocked[cross] || body.touching[cross]` → SKIP the snap this frame
     (a wall/tank is being resolved on that axis; snapping would fight Arcade — retry on the next
     clear turn). `TANK_SIZE = 92` is NOT a multiple of 24, so we snap the CORNER (not the center) to
     keep `laneIndex`/`target` exact and integer-clean.
   - Otherwise set `body.position[cross] = target` for THIS frame's one-shot re-center (a single
     discrete write on the turn, NOT a blended per-frame correction; the cross VELOCITY stays 0, so
     no diagonal). This is the only place the design touches `body.position`, and it is gated to the
     turn frame + the `!blocked/!touching` + dead-band conditions above, honouring D6's "Arcade owns
     the body / never fight the collider" contract.
5. **Visuals:** position `rect` + `barrel` to `body.center`; orient `barrel` along `facing`.

**BulletPool.acquire(owner, cx, cy, facing).** `find(!active)`; if none, return null (a dropped
shot is cosmetic, never a correctness bug — the pool is sized well above `MAX_PLAYER_BULLETS × 2
players`). Set `vx/vy` from `facing · BULLET_SPEED`; place at a small muzzle standoff ahead of the
tank along `facing`; mark active; store `ownerSide` + `owner`. (No `new` — reuse the member.)

**BulletPool.tick(dt).** For each active bullet: `rect.x += vx·dt; rect.y += vy·dt` (hand-
integrated, mirroring the reference so a future hit-stop can pass `dt=0` to freeze them); also nudge
the body so the out-of-bounds read is fresh. If the bullet's body is fully past the playfield bounds
(`PLAYFIELD_X..X+W`, `PLAYFIELD_Y..Y+H`), `release(rect)` → disable + `owner?.onBulletReleased()`.

**Tank.tryFire(pool).** If `cooldownTimer > 0` OR `liveBullets >= maxBullets`, return (no-op). Else:
`pool.acquire(this, muzzleX, muzzleY, facing)`; on success `cooldownTimer = FIRE_COOLDOWN;
liveBullets++`.
